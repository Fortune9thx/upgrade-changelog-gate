# Design

Deep explanation of UpgradeChangelogGate's consensus mechanism, why it takes the shape it does, and the trade-offs made along the way. The README covers the interface; this document covers the reasoning.

## The core problem this contract solves

Every upgradeable protocol needs a way to move a version pointer, and every such move comes with a changelog someone wrote to explain it. The changelog is prose; the actual change is a fact. Nothing today forces those two to match except a human reader's attention span, and a proposer who wants to smuggle an undisclosed change past reviewers only has to write past a skim, not past a real check. This contract exists to make "does the changelog match the actual diff" a question independent, non-colluding validators answer -- not a question one reviewer, however careful, answers alone.

## Why the diff is computed once, deterministically, outside the non-deterministic block

This is the single most consequential design decision in the contract, and it is a deliberate departure from the shape of this account's other GenLayer primitives (which fetch live, genuinely unpredictable web evidence inside `leader_fn`/`validator_fn` because a web page's content can differ from one fetch to the next). Here, the two things being compared -- the protocol's stored `content` and the proposal's stored `new_content` -- are both already-written, already-consensus-agreed blockchain state by the time `evaluate_proposal` runs. Diffing them is pure, deterministic Python: every node that executes this transaction computes the byte-identical diff, the same way any other plain contract-state read is identical across nodes. There is nothing here that legitimately varies between independent executions except one thing: the LLM's reading of whether the changelog is honest about that already-fixed diff. That is the only call inside `gl.vm.run_nondet_unsafe`'s closures. Computing the diff outside it is not a shortcut -- redoing a deterministic computation inside a non-deterministic block would add latency and code complexity for zero additional guarantee, since every validator would just recompute the identical answer anyway.

This also makes the design more efficient than an evidence-fetch-based one: there is no redundant per-validator network fetch anywhere in this contract, because there is no web fetch at all. The only non-deterministic primitive either role calls is `gl.nondet.exec_prompt`, once each.

## Why independent re-derivation is still mandatory for the one thing that IS non-deterministic

Even though the diff itself can't be gamed, the *verdict* about it still could be, if validators only checked that the leader's claimed verdict was one of the three valid strings. `validator_fn` does not do that -- it calls the identical `leader_fn` again, over the identical diff and changelog (already fixed by already-agreed state), and only agrees if its own, independently-run LLM judgment lands on the same bucket. A leader who fabricated `"FAITHFUL"` for a changelog that plainly omits a disclosed field has no path to acceptance: the validator's own fresh read of the same diff and changelog would land on `"INCOMPLETE"` or `"MISLEADING"` instead, and the round fails to reach agreement.

## Why three discrete buckets, not a free-form honesty score

Two independent LLM calls over the same diff and changelog will not produce identical prose, and asking for a continuous score (e.g. "85% honest") would make consensus fail for reasons unrelated to whether the underlying judgment was sound. `FAITHFUL` / `INCOMPLETE` / `MISLEADING` gives independent validators a small, shared vocabulary two honest, independent readings are likely to converge on, while still distinguishing three genuinely different situations: full disclosure, honest-but-partial disclosure, and an active contradiction of the diff. The bucket -- and only the bucket -- is what `validator_fn` compares and what the contract acts on (stake routing, pointer-flip eligibility); the free-text `reason` is stored for human context but is never part of the equivalence check, for the same reason documented in this account's other primitives: forcing exact-text agreement on LLM prose would make consensus fail for reasons that have nothing to do with whether the judgment itself was sound.

## Why GenLayer's role stops at "is the changelog honest," never "is the upgrade good"

This is the sharpest scope boundary in the whole design, and it is deliberate. "Is this changelog an honest account of this diff" has a ground truth neither party authored alone -- the diff. "Is this upgrade a good idea" has no ground truth at all; it is a policy judgment, and asking an LLM to make it would be exactly the open-ended "AI decides X" shape GenLayer Portal review does not want to see, with no bounded, checkable question underneath it. `accept_proposal` keeps that decision with the protocol's own owner, gated only on the objective fact that the changelog was independently verified honest -- GenLayer never decides whether to apply the upgrade, only whether the account of it in front of the decision-maker is accurate.

## Non-determinism boundaries

`evaluate_proposal` contains exactly **one** top-level non-deterministic call: `gl.vm.run_nondet_unsafe(leader_fn, validator_fn)`. `leader_fn`/`validator_fn` are both ordinary named `def`s, never `lambda`s -- `genvm-lint` enforces this as a hard static-analysis rule, and a lambda leader is flagged as a nested-nondeterminism violation even when it is the only non-deterministic call in the method. Neither closure reads or writes `self.*` storage; `diff`, `changelog`, and `flagged` are plain locals copied from the already-loaded `proposal` record before the non-deterministic section begins.

## Calldata safety

Unlike a numeric outcome scale, `verdict` is matched against a fixed three-string vocabulary directly -- there is no clamp/snap arithmetic anywhere in `_coerce_verdict`, which structurally avoids an entire class of numeric-edge-case bug (a non-finite float silently resolving to an unintended bucket) that a 0-100 scale would need explicit guards against. No public method ever returns a raw `dict`; `get_protocol`/`get_proposal` both return JSON-encoded `str`, so no return value can ever carry an un-encodable float, structurally rather than by convention.

## Storage

`TreeMap[str, str]` only, matching the only value type with reliable post-deploy readability on the current GenVM build behind Bradbury. `protocols` and `proposals` store JSON-encoded records; `protocol_latest_proposal` maps a protocol's normalized key to its most recently submitted proposal_id (a convenience index, not an identity claim -- see "Trust boundaries" below for why this needs no ownership protection the way a claim-identity index would). `proposal_counter` is the one genuinely scalar field and uses `u256` directly.

## Input validation

`protocol_id` must match `^[a-z0-9][a-z0-9_-]{0,63}$` -- a deliberately narrow format that structurally rules out an entire class of problem this account's prior primitives had to discover and patch after the fact: there is no free-text claim-identity field here for a Unicode-encoding or homoglyph trick to exploit, because the format itself only permits lowercase ASCII letters, digits, `_`, and `-`. `_protocol_key`'s NFC normalization is still applied for defense in depth, but for an always-ASCII input it is a proven-harmless no-op, not load-bearing. `content`/`new_content` must be flat JSON objects with 1-20 string-keyed, JSON-scalar-valued (string/int/bool/null) fields -- see `_validate_content`'s docstring in the contract for why nested values are out of v1 scope and how a protocol that needs to version nested configuration can still use this primitive (store a content hash reference and diff against that). `changelog` is non-empty and length-capped.

## Trust boundaries

- **The diff cannot be gamed by the proposer -- only the changelog about it can be dishonest.** `new_content` is proposer-supplied, but the diff is computed against the protocol's actual stored `content`, not anything the proposer claims about it. A proposer cannot fabricate a favorable diff; they can only write a changelog that misdescribes the real one, which is exactly the question this contract exists to check.
- **`changelog` is caller-controlled prose and gets the same scrutiny this account's other primitives give any caller-supplied instruction-adjacent field.** A proposer could write a changelog instructing the model to ignore the diff or classify a certain way. The prompt explicitly frames the diff as ground truth and the changelog as an unauthoritative claim, and instructs the model to treat any embedded instruction-like text as evidence of `MISLEADING` intent. A heuristic scan (`_MANIPULATION_PATTERNS`, the same proven pattern used in this account's IndependentEvidenceSettler and Helm projects) flags obvious attempts as a transparency signal on the stored record -- **never a rejection gate**, and, stated plainly rather than implied: this catches only literal, unsophisticated phrasing and is trivially bypassed by paraphrasing. The real defense is the model's own compliance with the prompt instruction, which no contract code can enforce -- the same honest limitation documented in this account's other LLM-judgment primitives.
- **Protocol-name registration front-running is a real, accepted, standard limitation, not something this contract's code can prevent.** Anyone who sees a pending `register_protocol` transaction in a public mempool could in principle submit a competing registration for the same `protocol_id` first. This is the same class of risk as any first-come name-registration system (e.g. ENS squatting) and is not specific to this contract; closing it would need a commit-reveal registration flow, out of scope for v1.
- **A protocol owner proposing a dishonest upgrade against their own protocol makes the stake-forfeiture penalty a no-op against themselves.** If `proposer == owner` and the verdict is `MISLEADING`, the forfeited stake is transferred to the owner, i.e. back to the proposer. This is a genuine, deliberately-disclosed economic curiosity, not a security hole: the contract's actual guarantee -- the content pointer never flips on a non-`FAITHFUL` verdict -- holds regardless of who proposed the change or where the stake goes, so an owner gains nothing from self-dealing here that they couldn't already "achieve" (i.e. nothing) by simply not staking at all. The stake mechanism's real purpose is deterring a *different* party from gaming governance with a dishonest changelog, and it does that fully; it was never meant to punish an owner for lying to themselves.
- **`protocol_latest_proposal` needs no ownership protection the way a claim-identity index would.** Unlike this account's IndependentEvidenceSettler, where an unscoped "latest for X" index let a different sender shadow another sender's claim, proposing here is deliberately permissionless by design -- there is no legitimate-vs-illegitimate proposer to protect between, only an honest-vs-dishonest changelog, which the verdict itself already settles. "Latest proposal for this protocol" correctly means exactly that: the most recent one submitted, fully retrievable regardless of who submitted it or what its verdict was.
- **The model's raw output is never trusted directly.** `_coerce_verdict` defensively parses and validates the verdict against the fixed three-value vocabulary regardless of what the model returned, with a fail-closed default of `"INCOMPLETE"` for anything unparseable -- deliberately neither the trusting extreme (`"FAITHFUL"`, which would grant unearned trust to unparseable output) nor the punitive extreme (`"MISLEADING"`, which would forfeit a proposer's stake over a model or infrastructure hiccup that is not evidence of dishonesty). Matching is case-insensitive (`.strip().upper()`) so a model that writes `"Faithful"` instead of `"FAITHFUL"` isn't penalized for a casing inconsistency that has nothing to do with honesty -- found in a strict post-build review; fixed with zero change to the fail-closed direction, since the canonical uppercase string is always what gets stored regardless of the model's casing.
- **A defensive check exists for a state that cannot currently be reached.** `evaluate_proposal` and `accept_proposal` both re-check that the proposal's protocol still exists, even though this contract has no `delete_protocol` method and registration is permanent -- so that branch is currently dead code. Kept anyway as forward-compatible defense in depth (and because "assume the invariant always holds" is exactly the kind of assumption worth not making silently), stated here explicitly rather than left for a future reviewer to wonder about.
- **`accept_proposal` is bound to the exact protocol version its proposal's diff was computed against, closing a real stale-overwrite bug found in a strict post-build review.** As originally shipped, `accept_proposal` applied `proposal["new_content"]` unconditionally -- with a permissionless proposal flow, nothing prevented two proposals from being submitted against the same baseline before either was accepted. Accepting the first correctly advanced the protocol; accepting the second afterward would silently overwrite the protocol's content with a diff computed against the now-stale first baseline, discarding whatever the first upgrade changed for any field the second proposal didn't also happen to touch -- a real "lost update" bug, not a hypothetical one, and exactly the kind of gap a genuinely careful reviewer of the state model would find. Fixed by storing `based_on_version` on every proposal at `propose_upgrade` time and rejecting `accept_proposal` outright if the protocol has since moved to a different version, with an explicit message telling the proposer to submit a fresh proposal instead. Regression-tested (`TestStaleProposalGuard`) by actually reproducing the two-competing-proposals scenario and asserting the clobber does not happen, not merely that the ordinary path still works.

## Third benchmark pass (2026-08-23) -- re-screened for governance/staking-shaped patterns

The second audit pass above found this contract's own bugs by reading its own code adversarially. This third pass instead re-read `tendercouncil`, `spec-compliance-bounty`, and `rubricproof-intelligent-contract` a second time -- the same three independently-accepted Portal submissions already benchmarked while originally designing this contract (see "Originality" below) -- specifically hunting for governance/staking/versioning-shaped patterns relevant to *this* contract's actual shape, rather than re-deriving the evidence-fetch-focused findings (SSRF defense, CI enforcement) that a first benchmarking pass over the same repos already surfaced for this account's IndependentEvidenceSettler primitive.

**Finding 1 -- adopted: event emission for lifecycle tracking.** `spec-compliance-bounty` defines `gl.Event` subclasses (`CasePosted`, `SubmissionJudged`, `CaseResolvedMet`, `CaseCancelled`, `CaseExpiredTimeout`, `CaseExpiredExhausted`) and emits one after every state-mutating write, using up to 3 positional (indexed) constructor args plus a `**blob` kwarg for extra fields. UpgradeChangelogGate shipped with none. This is not a correctness requirement -- this account's own already-accepted IndependentEvidenceSettler has zero events and was still accepted -- and neither `tendercouncil` nor `rubricproof-intelligent-contract` use events either, so it is not a pattern all three repos converge on. It is, however, a genuine, low-risk strengthening of the "would someone import this" criterion this design already leans on: an off-chain indexer or frontend can now track protocol registration, proposal submission, evaluation, and acceptance without polling every `proposal_id` individually. Added `ProtocolRegistered`, `ProposalSubmitted`, `ProposalEvaluated`, `ProposalAccepted`, and `StakeRequirementUpdated`, each emitted immediately after the state write(s) it reports (and after any GEN transfer, matching the ordering observed in `spec-compliance-bounty`'s own `CaseExpiredTimeout` handler). Confirmed by inspection that `spec-compliance-bounty`'s own direct-mode test suite does not assert on emitted events either -- consistent with `gltest`'s WASI mock not being the layer that verifies event delivery -- so no new tests were needed here; all 50 existing tests pass unchanged against the new code, and `genvm-lint check`/`typecheck` remain clean.

**Finding 2 -- considered, no code change needed: permissionless timeout-gated refund escape.** `spec-compliance-bounty` ships `reclaim_exhausted_case` (callable by anyone once an attempt budget is exhausted) and a `CASE_TIMEOUT_SECONDS`-gated permissionless refund, because its funds-release path requires a submission being independently judged `MET` -- a step that can stall forever if a poster's case attracts no submissions, or a submitter never triggers judgment. Traced this contract's own equivalent path deliberately rather than assuming it's fine by analogy: the analogous funds-release step here is `evaluate_proposal`, which is already permissionlessly callable by **anyone** (including the proposer themselves, who has direct financial incentive to call it) and, once it runs to completion, unconditionally resolves the staked GEN -- `FAITHFUL` or `INCOMPLETE` refunds the proposer, `MISLEADING` forfeits to the owner -- entirely before any owner-gated step (`accept_proposal`) is ever reached. There is no state in this contract where a stake's release depends on an action only a specific, possibly-absent party can take: a vanished protocol owner blocks `accept_proposal` (the upgrade itself never applies), but does not strand the stake, which was already resolved by `evaluate_proposal`. No timeout mechanism was added, since bolting one onto a release path that already has no stuck-funds condition would be exactly the kind of defensive code for an unreachable state this design has already deliberately chosen, in one other case, to disclose plainly rather than hide -- and here, unlike that one case, there is no invariant worth guarding at all, so nothing was added.

**No other new findings.** Neither `tendercouncil` nor `rubricproof-intelligent-contract` introduced a governance, staking, or state-versioning pattern beyond what this contract's `based_on_version` guard (closed in the second audit pass) and existing stake-routing logic already cover.

**Redeployment note.** Both changes above are purely additive and deterministic -- new `gl.Event` subclasses and `.emit()` calls after existing state writes; no change to `leader_fn`, `validator_fn`, `_compute_diff`, `_coerce_verdict`, or any validation/authorization logic. The live Bradbury transaction record below (`register_protocol` → `propose_upgrade` → `evaluate_proposal`, all genuinely unscripted) therefore still stands as live proof of the non-deterministic mechanism for this redeployment; it was not re-run, since nothing about the mechanism it exercises changed.

## Steward review (2026-08-24) -- a real liveness gap this account's own third benchmark pass got wrong

A GenLayer Portal steward requested changes before continuing review, with this exact finding: *"The changelog verdict is independently re-derived and correctly gates both stake routing and upgrade eligibility, but a proposal's stake can remain locked forever if evaluation never reaches validator agreement. Please add a bounded cancellation or expiry path for still-pending proposals that returns the recorded stake exactly once, cannot run after evaluation, and cannot bypass a resolved forfeiture."*

This directly overturns "Finding 2" of the third benchmark pass above, which concluded no such escape hatch was needed here. Stated plainly, not smoothed over: **that conclusion was wrong, and the reasoning error is worth naming precisely.** The third pass correctly observed that `evaluate_proposal` is permissionlessly callable by anyone and unconditionally resolves the stake once it *completes* -- and then incorrectly treated "permissionlessly retriable" as equivalent to "guaranteed to eventually resolve." Those are not the same claim. `evaluate_proposal`'s own docstring already said, from the first commit, that if independent validators never reach agreement, no state is written and the proposal stays `"pending"` -- retriable, but with no bound on how many times, or for how long, that can keep happening. A genuinely ambiguous diff/changelog pair, or a persistent validator-infrastructure issue, could in principle cause every attempt to fail to reach agreement indefinitely, and nothing about permissionless retriability puts a ceiling on that. The steward's review caught a real gap this account's own internal audit and two benchmark passes did not.

**The fix: `reclaim_expired_proposal`, a bounded, permissionless escape hatch.** Once a proposal has been `"pending"` for at least `PROPOSAL_EVALUATION_TIMEOUT_SECONDS` (72h, matching the timeout window this account had already benchmarked from `spec-compliance-bounty`'s own `reclaim_exhausted_case`/`CASE_TIMEOUT_SECONDS` pattern during the third pass -- ironically, without adopting it at the time), anyone may call `reclaim_expired_proposal` to refund the proposer's stake and mark the proposal `"expired"`, a third terminal status distinct from `"evaluated"`.

Meeting the steward's three explicit requirements directly:
- **"Returns the recorded stake exactly once"**: `reclaim_expired_proposal` requires the identical `status == "pending"` precondition `evaluate_proposal` itself requires, and both methods flip status away from `"pending"` before any GEN transfer. Whichever of the two executes first permanently forecloses the other -- there is no interleaving under which both can run.
- **"Cannot run after evaluation"**: once `evaluate_proposal` completes, status is `"evaluated"`, which fails the same precondition -- `reclaim_expired_proposal` rejects outright, regardless of elapsed time.
- **"Cannot bypass a resolved forfeiture"**: a `MISLEADING` verdict's forfeiture happens *inside* `evaluate_proposal`, before status ever leaves `"pending"` in that transaction -- by the time status would allow a second look, the forfeiture (or refund) has already happened and `reclaim_expired_proposal`'s own precondition blocks it from running at all.

**A genuine technical question worth answering directly: is comparing two different clock-exposure paths safe?** `submitted_at` is stored via `gl.message_raw.get("datetime", "")`, unchanged from before. The new "now" reading inside `reclaim_expired_proposal` uses `datetime.now(timezone.utc)` instead, following the exact pattern `spec-compliance-bounty` uses for its own timeout window. This was a deliberate choice, not a convenience: `gltest`'s direct-mode mock does not propagate `direct_vm.warp()` into the live `gl.message_raw` dict a running contract call sees (confirmed by reading `gltest`'s own `vm.py` -- `warp()` updates `self._datetime` and calls `_refresh_gl_message()`, which only refreshes `sender_address`/`origin_address`, never `datetime`), so a test relying on `gl.message_raw`'s frozen datetime for both sides of the comparison cannot simulate elapsed time at all. `datetime.now()`, by contrast, genuinely is warpable in this test framework -- and is explicitly, deliberately sanctioned as deterministic in real GenVM execution: `genvm-lint`'s own `safety.py` source lists `time.time`/`time.localtime`/`time.gmtime`/`uuid.uuid1`/`uuid.uuid4` as forbidden non-deterministic calls (rule W002), with the adjacent comment *"Note: datetime.now() is OK in GenLayer - SDK provides deterministic version"* -- confirmed directly from the linter's source, not inferred from one repo's docstring alone. Both `gl.message_raw['datetime']` and `datetime.now()` expose the same underlying per-transaction consensus time, just via different SDK surfaces; mixing them for a 72-hour-scale threshold comparison introduces no meaningful risk even if some negligible skew existed between the two exposure paths. No other timestamp in this contract was changed -- `registered_at`/`submitted_at`/`evaluated_at`/`applied_at` all still use `gl.message_raw.get("datetime", "")` exactly as before.

8 new regression tests (`TestExpiryReclaim`) reproduce every one of the steward's three requirements directly: reclaiming before the timeout fails; reclaiming after it succeeds and refunds correctly (including the zero-stake case, which correctly skips the transfer); an already-`"evaluated"` proposal can never be reclaimed regardless of elapsed time (proves "cannot bypass a resolved forfeiture"); an `"expired"` proposal can never subsequently be evaluated (proves the exactly-once guarantee from the other direction); a second reclaim attempt on an already-expired proposal fails; the call is genuinely permissionless (exercised via a non-proposer sender); an unknown `proposal_id` is rejected. All 58 tests pass, `genvm-lint check`/`typecheck` remain clean.

## Live verification

Everything above this point was verified against `gltest`'s deterministic WASI mock -- which proves the contract's *logic* is correct given a scripted model response, but not that the actual, non-deterministic consensus mechanism converges on a genuine, unscripted judgment call. A strict review should not take that convergence claim on faith; a full register → propose → evaluate sequence was run live on Bradbury against `0x60553Fb5BAE7E4681a330169e2c17E8dde414f97`.

**1. `register_protocol`**, tx [`0xde235b869c...45ac5b35`](https://explorer-bradbury.genlayer.com/tx/0xde235b869c6f3852238d6265c610efc170b92a534622f5af4a3dfaced39c74c1) -- `ACCEPTED`/`AGREE`/`FINISHED_WITH_RETURN`. Registered `demo-protocol` with `{"fee_bps": "30", "admin": "0xOldAdminAddress000000000000000000000001"}`, `min_proposal_stake = 0`.

**2. `propose_upgrade`**, tx [`0x326d9da525...ab7c51400`](https://explorer-bradbury.genlayer.com/tx/0x326d9da525e9acd4c461d900edafb790161b3239e1cdae962329a76ab7c51400) -- `ACCEPTED`/`AGREE`/`FINISHED_WITH_RETURN`. Proposed the deliberately adversarial scenario: `new_content = {"fee_bps": "50", "admin": "0xNewAttackerAddress00000000000000000002"}`, `changelog = "Increased fee_bps from 30 to 50 to fund development."` -- silently omitting the admin-field change entirely. The contract's own deterministic diff correctly captured both changes regardless of what the changelog said, producing `proposal-0`.

**3. `evaluate_proposal`**, tx [`0x36a0f4d362...d574c761`](https://explorer-bradbury.genlayer.com/tx/0x36a0f4d362dcb95efebd7c56b279d6fc8ca4d5980640e8ab28a27ac8d574c761) -- `ACCEPTED`/`AGREE`/`FINISHED_WITH_RETURN`, finalized in round 0. The stored, consensus-agreed result, read back directly from contract state after finality:

```json
{
  "verdict": "INCOMPLETE",
  "reason": "The changelog describes the fee_bps increase from 30 to 50 but omits the modification of the admin field from 0xOldAdminAddress... to 0xNewAttackerAddress..., a critical change not mentioned.",
  "diff": [
    {"field": "admin", "change": "modified", "old_value": "0xOldAdminAddress000000000000000000000001", "new_value": "0xNewAttackerAddress00000000000000000002"},
    {"field": "fee_bps", "change": "modified", "old_value": "30", "new_value": "50"}
  ]
}
```

**Why `INCOMPLETE`, not `MISLEADING` -- a real finding worth stating plainly, not smoothing over.** Before this test ran, the project's own working narrative (and an earlier draft of the test suite) assumed this exact scenario -- an undisclosed admin-key change -- would be judged `MISLEADING`. The live model call disagreed, and on inspection, the live model was right and the original assumption was imprecise: the contract's own bucket definitions say `INCOMPLETE` is for a changelog that "omits at least one field that actually changed," and `MISLEADING` is for one that "makes a claim that contradicts the diff." This changelog never claims anything false about the admin field -- it simply never mentions it. That is squarely omission, not contradiction, by the contract's own stated rules, and the model applied that distinction correctly and precisely, citing the exact field it found undisclosed. The test suite (`tests/direct/test_upgrade_changelog_gate.py::TestSignatureScenario`) was corrected to match this real, verified behavior rather than the original assumption, and a second test was added for the sharper case -- a changelog that actively, falsely claims the admin field "was not changed" -- which is the scenario that actually fits `MISLEADING`'s definition of contradicting the diff outright.

**What this proves, and what it does not.** It proves the mechanism works end to end on real Bradbury consensus: a genuinely non-scripted model call correctly read a deterministic diff, correctly applied the contract's own three-way distinction to a real adversarial case, cited specific evidence in its reasoning, and independent validators reached binding agreement on that exact verdict, which was then durably written to contract state. It does not, from a single run, establish a statistical convergence rate across many rounds or prove liveness under adversarial network conditions -- one genuine live data point is meaningfully more evidence than zero, and is presented as exactly that, not as an exhaustive live audit.

**Redeployment note (stale-proposal guard + case-insensitive verdict fixes).** The fixes documented above in "Trust boundaries" changed only deterministic code -- `propose_upgrade`'s record construction (adding `based_on_version`) and `accept_proposal`'s pre-write validation, plus `_coerce_verdict`'s string comparison. `leader_fn`/`validator_fn` themselves, and the underlying `gl.vm.run_nondet_unsafe` consensus mechanism the live run above exercised, are unchanged. The transaction record above therefore still stands as the live proof of the non-deterministic mechanism for the redeployed contract; the new deterministic guards are proven instead by `TestStaleProposalGuard` and `TestVerdictCoercion`'s case-insensitivity tests actually reproducing the scenarios they close, per the same "regression-tested, not just happy-path-tested" standard applied throughout this project.

**Redeployment note (steward-requested expiry path).** `reclaim_expired_proposal` is an entirely new method, not a modification of `evaluate_proposal`, `leader_fn`, or `validator_fn` -- the non-deterministic mechanism the live run above exercised is byte-for-byte unchanged. The transaction record above still stands as the live proof of that mechanism; the new expiry path is proven instead by `TestExpiryReclaim`'s 8 regression tests, which directly reproduce the steward's three stated requirements (exactly-once refund, cannot run after evaluation, cannot bypass a resolved forfeiture) rather than merely asserting the happy path.

## Originality

Screened against every primitive this account has already built or benchmarked against while designing this one:

- **This account's IndependentEvidenceSettler**: judges whether *externally fetched web evidence* supports a *claim* under caller-supplied *criteria* -- evidence comes from the outside world and the judged question is "does this evidence support this claim." This contract has no web fetch at all; the judged artifact is a *deterministically-computed diff of already-stored blockchain state*, and the judged question is "does this prose match this diff" -- a categorically different evidence source and a narrower, more bounded question.
- **This account's Equiv (`Claim.py`)**: a staked capital market where positions are taken for/against a claim's outcome, resolved by consensus reading live evidence against creator-set criteria. This contract has no staked positions on an outcome and no market -- the stake here is a flat anti-spam/anti-dishonesty bond on a single proposer's own action, forfeited or refunded based on an objective honesty check, not a market resolution.
- **This account's AgentIntentSettlement**: judges whether an agent's claimed action fulfilled a natural-language goal, using submitted evidence, and executes an escrow consequence across five possible actions. This contract's judged question is comparative-and-bounded (prose vs. a fixed diff) rather than open-ended (does evidence show goal fulfillment), and has a simpler, two-outcome-shaped value flow (forfeit or refund) rather than a five-way escrow disposition.
- **`tendercouncil`, `spec-compliance-bounty`, `rubricproof-intelligent-contract`** (independently accepted GenLayer Portal submissions, benchmarked directly while designing this contract): none judges a changelog against a deterministic diff of contract-native state. `spec-compliance-bounty`'s own `docs/DECISION_RECORD.md` explicitly screened and discarded a closely-related idea ("Upgrade-diff governance: a proposed upgrade must ship a changelog; judgement asks 'does this diff genuinely match its changelog' before an upgrade pointer is allowed to flip") as their own documented fallback candidate -- confirming independently that the underlying idea passes every screening gate on its own merits, while leaving it unbuilt and open. This contract is a from-scratch, independently-designed implementation of that same underlying concept, not a copy of any code from that repo.
